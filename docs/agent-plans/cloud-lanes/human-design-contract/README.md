## Versioned save and control semantics

The three checked-in Draft 2020-12 JSON schemas are generated by `generate-schemas.mjs`. `contract.mjs` reads those schemas using a deliberately limited validator that rejects unimplemented schema keywords. An independent check uses the environment’s existing Python `jsonschema`; no new packages were installed.

`HumanDesignSaveV2` is `{ schemaVersion: 2, legacyLook, design: { controlSpace: 'legacy-relative-v1', morphology, expression } }`. The legacy look preserves parsed values, existing wearables and omission semantics; JSON whitespace/property order are not preserved. The design is a detached proposal, not a new canonical player record.

Every morphology leaf is a finite scalar in `[-1, 1]`, default `0`. Negative and positive values select separately authored endpoint deltas. **These are normalized authoring coordinates, not metres, demographic averages, accepted anatomy limits or a license to scale every bone.** Zero means no new change to the normalized legacy appearance. Skin, mesh key, hair, clothes, age presentation and expression never choose a morphology preset implicitly.

| Group | Positive endpoint meaning; negative endpoint is the opposite | Dependencies before a renderer may enable it |
| --- | --- | --- |
| `earLeft`, `earRight` | `height` taller; `width` wider; `protrusion` farther from head; `rotation` helix turned forward; `lobeLength` longer | Independent lateral deltas, continuous ear-root seam, accessory/scalp collision; no implicit mirroring |
| `nose` | `bridgeWidth` wider; `bridgeHeight` higher bridge; `projection` forward tip; `tipRotation` upturned tip; `alarWidth` wider nostril base | Bridge/tip/alar regions, nostril wall, profile and upper-lip corrections |
| `face` | `width` wider face; `length` longer face; `headDepth` deeper cranium; `jawWidth` wider jaw; `chinProjection` forward chin; `cheekFullness` fuller cheeks | Stable skull/neck connection, teeth/jaw alignment and scalp fit |
| `face`, continued | `browHeight` higher brow; `browAngle` outer brow raised; `eyeSpacing` farther apart; `eyeAperture` wider open neutral lids; `eyelidFold` more pronounced fold; `lipFullness` fuller lips | Eyeball/lid/socket placement, brow and blink corrections, lip seal and mouth cavity |
| `body` | `height` taller; `shoulderWidth` wider shoulders; `torsoLength` longer trunk; `armLength` longer arms; `legLength` longer legs; `waistWidth` wider waist; `hipWidth` wider hips; `handSize` larger hands; `footSize` larger feet; `abdominalFullness` fuller abdomen; `muscleDefinition` more visible surface definition | Rig-length/rest/bind corrections, volume-preserving joint shapes, gait and seat/contact recalibration, body/cloth fitting. No strength, health or identity inference |

There are 38 independent scalar controls. The owner must replace endpoint descriptions with signed landmark measurements, shape hashes and allowed combinations on its accepted topology. Do not guess a universal “10%” range. UI labels may offer an explicit link-left/right action; this schema always stores both ears separately.

Saved expression is `{ preset, intensity }`; intensity is `[0,1]`. Presets: inherit, neutral, soft-smile, grin, focus, concern, surprise. `inherit` takes the **already normalized** legacy expression from the current normalizer; the helper defaults to smile, matching the saved-look default. The 16 output channels separate left/right smile, frown, brow raise/lower, blink, jaw open, lip seal/pucker/wide and signed gaze yaw/pitch. Channels are expression goals, not an assertion of existing morph targets or FACS certification.

Every expression sample starts fresh. Sleep closes lids and suppresses other channels; lip seal attenuates jaw opening; lip pucker/wide share a sum-at-most-one budget. Independent blink, speech and gaze are transient host input and cannot be serialized in the expression record. Gaze uses normalized `[-1,1]`; its angle range awaits the eye rig. Basic speech shapes are composition fixtures, not a phoneme recognizer or a complete language/viseme set. The host supplies time; this package starts no loop.

## Save lifecycle and migration

- `createSave(legacyLook)` supplies all zero residuals and inherit expression without changing legacy values. Empty `{}` remains empty, preserving seeded defaults.
- `encodeSave` validates and sorts object keys recursively; arrays retain order. `readSave` validates the whole v2 envelope. Both cap serialized input at 16,384 UTF-8 bytes.
- `migrateSave` treats an object without `schemaVersion` as the existing legacy look (version 0). Prototype v1 is explicitly a **hypothetical earlier experiment**, never a shipped game format; its bilateral `ears` group copies to two independent objects. V2 migration is idempotent.
- Unknown versions, unknown fields, malformed data and non-finite/out-of-range writes fail with `ContractError`. Retain original bytes and request repair; never save a blank default over an unreadable version. Migration itself performs no storage writes.
- `withControl` is strict. `withClampedControl` is an editor-only adapter for finite overshoot: it returns `{ save, applied, clamped }`, so the UI can display the applied value. This satisfies the plan’s editor-clamp behavior without silently changing network/saved data. Non-numeric input still fails.
- Existing parent code must validate legacy IDs, slot conflicts and inventory authorization. The retained legacy fields permit bounded strings/indices deliberately so migration does not reinterpret older aliases. Passing this experiment’s schema alone is insufficient for a game API write.

Before production persistence: owner defines the exact optional field in Look, server allowlist, public projection, byte limits, atomic last-known-good save behavior and migration marker. Replaying the same original bytes must return the same result; preserve originals until successful round-trip and rendered-identity review. If an asset tier cannot express a control, keep the saved design and use the approved legacy fallback; do not erase it or claim the feature rendered. Topology migration needs an explicit versioned correspondence and fit revalidation, not a copied vertex array.

## Hair, clothing and the proposed rig/anchor binding

`allworld-body-23@1` is this proposal’s label for the inspected family, **not a newly approved rig registry entry**. Both current meshes use its names, but attachment packets additionally pin body SHA-256, topology ID, topology SHA-256, anchor revision and triangle count. The owner must define `topologySha256` over the canonical ordered, decoded vertex/index domain; a GLB metadata hash is not that hash. The actual source GLB hash pins rest/bind data. No production anchor packet is supplied.

Fourteen named surface anchors cover all 11 existing wardrobe slots. `REQUIRED_ANCHORS` and `ANCHORS` in `definitions.mjs` declare slot coverage, support joint and local-fitting dependency hints. Those hints are not a complete cache invalidation graph: every morphology, bind, pose or global scale change must reevaluate every anchor, including scalp/ear anchors after a body-height change. Bilateral groups must resolve both anchors even if an individual accessory uses one side. This prevents an accidental missing-side fallback; it does not require identical left/right accessories.

Each binding has triangle index, barycentric coordinates summing to 1, and outward normal offset in metres. Frame: body-local metres, Y up, Z forward; placement/scene scaling happens later. Evaluate the barycentric surface **after identity and expression deformation**, then skin using the actual weighted surface; the named joint is a validation/support hint, not permission to rigidly parent everything to Head. Transform normals correctly under non-uniform scale. Bindings are rejected on mismatched mesh/topology/rig/version, unknown joint/slot, missing anchor, invalid triangle or invalid barycentric coordinates. Topology reorder, LOD changes or asset re-export require rebind/versioned correspondence.

`fixtures/synthetic-hair-bindings.json` references an invented four-triangle mesh and repeated placeholder hashes. It tests validation only and must never be loaded as a body attachment. Hair and clothes still need actual immutable asset IDs/hashes, fit deltas, masks, material/UV/normal dependencies, provenance, LOD correspondence and per-pose evidence in the receiving asset packet. Surface anchors alone do not fit a garment or solve collision.

The proposed deformation order is immutable base → legacy appearance → identity shapes and rig rest/bind corrections → fitted hair/clothing and their corrective shapes → expression shapes → raw clip sampling/checkpoint restore → skinning/pose corrective shapes → host contact correction → scene placement. Exact ordering of corrective shapes and anchored attachments must be agreed with the body owner and verified on actual geometry. A new jaw/eye rig requires either compatible morph targets or an explicit tested retarget/version contract; the current 23 bones have no independent facial joints.
