# Hitches (long frames), 2026-10-17

Branch `perf`, dev server http://127.0.0.1:5191 (open-dev, unminified), headless Chromium 145 with the GPU (ANGLE Metal, Apple M4 Pro), 1280x800, deviceScaleFactor 1.

## Method

Recorder: `~/Documents/Allworld-notes/perf-tools/hitch-recorder (kept outside the repo: CI allows JavaScript only in reviewed files)/rec.mjs <base> <outPrefix> <cpuThrottle>` (a CDP script modelled on `/tmp/allworld-probes/shot-gpu.mjs`). Each run makes a fresh life and plays one scripted session:

| phase | what happens |
|---|---|
| load | page load at `/?diagnostics` until the neighbourhood (outside home) has drawn and settled |
| nbh-idle | stand still 4 s |
| nbh-walk | walk a square of 12 m steps for 20 s (`venue.walkTo`) |
| home-enter | `venue.walkHomeDoor()`, wait for `home`, 5 s |
| home-exit | `home.door outside`, wait for the neighbourhood, 5 s |
| travel-venue | travel to the market (if closed, the first open of i-fitness, mosque, Quilox), 6 s |
| venue-walk | walk a square of 10 m steps for 20 s |
| map | `shell.open('map')`, 6 s |
| map-close | `shell.close()`, 3 s |
| travel-home | travel home, step outside, 4 s |
| street-enter | `venue.walkStreetGate()`, wait for `city-street`, 6 s |
| street-walk | walk 60 m (30 m legs), stop |

- An injected script (before load) logs every requestAnimationFrame gap with the current phase, whether WebGL drew in that frame (wrapped `clear()` on canvases wider than 64 px), and Long Animation Frame entries over 33 ms with their scripts. The log survives page reloads (sessionStorage).
- Vite HMR `full-reload`/`update` messages are dropped inside the recorded page. Another agent was editing `canonical-crowd.ts` the whole time, and every save reloaded the page mid-session in the first attempts.
- The whole session is traced with `Tracing.start` (categories `devtools.timeline, v8.execute, disabled-by-default-devtools.timeline, gpu, v8, disabled-by-default-v8.cpu_profiler, blink.user_timing`). `trace.mjs` parses the trace line by line (traces are 250 to 580 MB). For every main-thread `RunTask` over 33 ms it reports the GC, layout, style and compile events inside it, and attributes the CPU samples in it to the innermost `/src/` frame, a GL call, or GC. `SUM=1` aggregates per phase; `DRILL=<frame>` shows the stacks under one frame. The GPU process main thread had no event over 17 ms in any run, so no hitch was GPU-side.
- Tiers: no throttle, and `Emulation.setCPUThrottlingRate` 4 (desktop size).
- Caveats: one session per tier per step, on a machine shared with another agent's headless probes and live edits to the crowd code, so counts of 33 to 50 ms frames vary by about ±30% between identical runs. The large hitches (over 250 ms) are stable. Before = the checkout at the start of this task (with the other agent's live edits). The first desktop "before" run (`d`) went to the gym, because the market was closed at that game hour. The comparison uses `d2`, which went to the market.

## What changed

1. **`src/scene/character-lab/runtime/characters.js`, `recoloredTexture`**: each output byte depends only on its channel and input byte, so a 256-entry table per channel replaces the per-pixel `pow`. Per-channel byte histograms replace sorting the sample lists (the median byte is the same). The output is byte-identical: `hitch-recorder/lut-check.mjs` checks 300 random and edge-case images plus a 1024x1024 one, with 0 mismatches. A 1024x1024 texture went from 158 ms to 3 ms.
2. **Same file, `bodyMask`**: decide hidden-ness once per vertex (a `Uint8Array`), then filter the triangles. The index list is identical (`bodymask-check.mjs`: 0 of 200 differ).
3. **New `src/scene/shader-warmup.ts`**, used by `src/venue-world.ts` (`renderScene`, marked on scene change, crowd ready and ambient arrival), `src/street/host.ts` (`draw`, marked on tile, overlay, stand-in and player changes) and `src/map3d/map3d.ts` (`draw`). Before a draw, if any material under the scene has no program yet, it calls `renderer.compile()` and polls `KHR_parallel_shader_compile` completion. The draw is skipped until the links finish (at most 1.5 s), then redrawn. Programs that are already linked do not hold the frame. Without the extension, or with the tests' stand-in renderers, nothing changes. The same programs are drawn, so nothing looks different. The difference is that links now run in parallel while the main thread stays free, instead of serially inside one frame. A plain frame only checks again after `mark()` or every 500 ms (one traverse). Tests: `src/scene/shader-warmup.test.ts`.

Tried and dropped: packing the AO occluders into typed arrays. It was byte-identical but 25% slower in V8 on a synthetic test, so it was not applied.

## Map first open

Opening the 3D map for the first time in a session used to run one main-thread task of 650 ms (about 1 s under the trace), then a string of 50 to 130 ms tasks from the world atlas.

Cause (trace, `rec.mjs` with `ONLY='^map$'`, plus timers inside `buildCity`): `createMap3D` built the city at once (600 ms on desktop). Of that, the estate layouts of all 20 local governments were about 320 ms (`estateLayout`: `pointInPolygon` on long boundary rings 224 ms, the grid fill `scanRings` 70 ms, `squareFree`), the fabric placing about 80 ms (`roadDistance` against every road segment), the baked vertex AO about 110 ms (`src/scene/build.ts` `bakeVertexAO`), the rest about 40 ms. The atlas (world map, built in the background) added tasks of 130, 65, 70, 65 ms: the level meshes, and `drawSheet` regenerating the route rows, each asking `allCityLinks()` again.

What changed, all in `src/map3d` (no look change; digests and layouts are checked equal):

1. `roads.ts pointInPolygon`: a ring of 48 or more points is sorted once into horizontal bands and a query tests only the edges of its band, with the same crossing arithmetic (`point-in-polygon.test.ts`: identical to the plain loop on 16,000 random and edge points).
2. `lga.ts scanRings`: edges are filed under the rows they can cross (`scan-rings.test.ts`: the same runs in the same order).
3. `city-build.ts`: `roadDistanceTo` (a grid with ring search that stops when nothing nearer can remain, the same minimum), and `buildCity` is now `buildCitySteps`, a generator paused at each section and every 64 fabric points; `buildCity` drives it to the end, so every other caller is unchanged.
4. `estates.ts`: `gridSteps` (the land grid in steps), `warm.ts` (`warmEstates`, `turn`), `map3d.ts prebuildCity` (kit, network, city in slices of 4 ms, with a MessageChannel turn between them) and a `prebuilt` option on `createMap3D`.
5. `index.ts mount`: builds through `prebuildCity` first, then hands the finished city to `createMap3D`. The map's `tabHidden` stays true until the player, state, people and camera are in (three short tasks), so the first frame drawn is the finished one, as before.
6. `geo/atlas.ts`: the level builders are generators (a level's layers stay out of the scene loop until the level is whole), driven in 4 ms slices one level at a time; the route rows look links up in one map per sheet.
7. `hitch-recorder/rec.mjs`: the CPU throttle did not hold after the page navigation and was dropped again during a run, so the earlier "CPU x4" columns in this file were partly unthrottled. It is now applied after the load, at every phase and every 300 ms (verified with a timed loop: 18 ms plain, 65 to 72 ms at x4). Also `PROBE=<prefix>` prints matching console lines.

## Background people baking (round 2)

The largest remaining source after the first round: background people's static bodies baked on the main thread (`canonical-crowd.ts`, `native-static-lod.ts`), 1.1 to 1.4 s of long tasks per session in this round's "before" runs. Also the neighbourhood's AO bake, repeated on every return.

### What changed

1. **New `src/scene/body/bake-slicer.ts`**: one cooperative budget for the page. Work runs in slices of at most 6 ms, one slice per frame, in a message task after the frame (rAF, then `MessageChannel`; a 250 ms timer keeps a hidden page moving). Without `requestAnimationFrame` (node tests) nothing is sliced. Tests: `bake-slicer.test.ts`.
2. **`canonical-crowd.ts makeTemplate`** starts at a fresh slice and checks the budget between steps: body spawn, pose capture, every 256 vertices of the skinning bake, each part's simplification, and the crowd's per-member placement and per-batch merge. The pose is captured in one step (bone skinning matrices, morph influences, world matrices, the materials), so later slices cannot see a different pose. The skinning repeats `SkinnedMesh.applyBoneTransform` operation for operation with each bone's matrix product formed once. The third skinning per vertex (`getVertexPosition`) is skipped when there are no morph targets, because it equals the first. Each mesh's geometry is copied when its turn comes, without the morph targets the bake drops anyway.
3. **No half-built crowd**: a crowd's meshes join its group in one step when the crowd is complete. A single figure was already added at once. While a figure is loading, it still shows nothing.
4. **Near detail**: a swap now re-merges only the wardrobe batches that hold a figure that changed. Before, every batch was re-merged. The merge uses typed arrays (`mergeBatch`) and gives the same attributes, order, index values and index type as `mergeGeometries`, which handles anything unusual. The swap still happens in the frame that asks for it.
5. **`characters.js`**: `spawnSliced()` (used only for a body that is baked and never drawn, via `createNativeBody(..., { sliced: true })`). It yields at slice points: after the rig, after each garment, between body-mask meshes, before the look, and in bands of rows inside a texture recolour. The same pixels are sampled, and each output byte depends only on its input byte. `driveSync`/`driveAsync` skip the slice points, so the player's and live NPCs' bodies run exactly as before. If an asset is missing, it falls back as before (preload the look, then load).
6. **Meshoptimizer in a worker**: new `native-static-lod-job.ts` (the WebAssembly part, shared code) and `native-static-lod.worker.ts`. `simplifyNativeStaticGeometryOffThread()` prepares the job and finishes the geometry on the main thread, in slices. If there is no worker or it fails, the job runs here, as before. The worker is 70 kB in the production build (`vite build` checked; Meshoptimizer only, no three.js). In production its CSP must allow `wasm-unsafe-eval`, or it falls back to the main thread, still sliced per part.
7. **`build.ts` AO**: baking into a buffer of ones gives exactly each vertex's factor. The factors are kept with the exact inputs (positions, normals, primitives, strength), up to 3 M numbers, and compared number for number. A rebuild with the same inputs (the neighbourhood on return) multiplies the colours by the kept factors: the same product the bake forms. AO depends only on these inputs, not on the colours.
