# Allworld character, animation, navigation, and physics research

Date: 2026-10-13
Repository baseline: `5179285a25cb616e9c8ef5b137150a5a6f6e05e7`
Scope: source-backed options that can improve gameplay movement, rendering, 3D animation, characters, or physics without replacing Allworld's existing scene contracts.

## Current seam and decision

The repository currently has Three.js `^0.180.0`, Vue 3, and no physics dependency in [package.json](/Users/anthonyakpan/Desktop/JoinAllworld/package.json:84). The procedural character system normalizes deterministic looks, supports low/medium/high detail, and can build a rig whose `poseAvatar()` only rotates existing parts ([characters.ts](/Users/anthonyakpan/Desktop/JoinAllworld/src/scene/characters.ts:1), [characters.ts](/Users/anthonyakpan/Desktop/JoinAllworld/src/scene/characters.ts:1501)). Keep that as the crowd and fallback path.

The skinned path already loads GLB bodies and clips lazily, samples clips through `AnimationMixer`, and has a dedicated two-bone foot-contact solver ([skinned.ts](/Users/anthonyakpan/Desktop/JoinAllworld/src/scene/body/skinned.ts:1), [foot-contact.ts](/Users/anthonyakpan/Desktop/JoinAllworld/src/scene/body/foot-contact.ts:18)). `createAnimationPoseCheckpoint()` deliberately restores mixer output before external IK ([animation-pose.ts](/Users/anthonyakpan/Desktop/JoinAllworld/src/scene/body/animation-pose.ts:3)). These are good integration seams: add solvers behind the body interface and keep authored clips, wardrobe, tinting, and the existing fallback intact.

Movement and camera are also intentionally cheap. `motion-loop.ts` is the only scene frame loop and stops when there is no live input or motion ([motion-loop.ts](/Users/anthonyakpan/Desktop/JoinAllworld/src/scene/motion-loop.ts:1)); camera occlusion uses allocation-free slab tests against boxes and people rather than per-frame mesh raycasts ([camera-collision.ts](/Users/anthonyakpan/Desktop/JoinAllworld/src/scene/camera-collision.ts:1)). Therefore the first recommendation is a narrow, opt-in controller probe—not a physics rewrite.

The concrete terrain gap is narrower than “no foot support.” Venue scenes expose `contactHeightAt()` that samples the highest rendered horizontal face and rejects synthetic navigation ramps ([venue-scenes.ts](/Users/anthonyakpan/Desktop/JoinAllworld/src/scene/venue-scenes.ts:916)); `venue-world.ts` forwards it to the skinned stand-in only when the avatar is not hopping, on stairs, locked, in an activity, or easing ([venue-world.ts](/Users/anthonyakpan/Desktop/JoinAllworld/src/venue-world.ts:1320)). Home also solves against its rendered/contact surface ([home-scene.ts](/Users/anthonyakpan/Desktop/JoinAllworld/src/scene/home-scene.ts:1105)). The neighbourhood scene and street host expose `heightAt() { return 0; }` and do not feed sampled foot contact ([neighbourhood-scene.ts](/Users/anthonyakpan/Desktop/JoinAllworld/src/scene/neighbourhood-scene.ts:218)); street tiles rebuild a 2D `WalkGrid` as tiles stream ([street/host.ts](/Users/anthonyakpan/Desktop/JoinAllworld/src/street/host.ts:94)). The opportunity is therefore street/neighbourhood terrain support and consistent step/slope semantics, not replacing venue foot solving wholesale.

## Strongest recommendations

### 1. Rapier TypeScript: future capsule controller and selective world physics

**Source and license.** Rapier is a real-time 2D/3D engine with rigid bodies, joints, sensors, soft bodies, snapshots, optional determinism, and JavaScript bindings; the project states that it is Apache-2.0 licensed ([Rapier overview](https://github.com/dimforge/rapier/blob/master/website/docs/about_rapier.mdx), [current repository](https://github.com/dimforge/rapier)). The old `dimforge/rapier.js` repository is archived and explicitly migrated into `dimforge/rapier` ([archive notice](https://github.com/dimforge/rapier.js)); use the maintained TypeScript package from the current repository rather than the archived repo. At this research date, npm reports `@dimforge/rapier3d-compat` 0.21.0 and explains that `-compat` embeds WASM as base64 for bundler compatibility ([npm package](https://www.npmjs.com/package/%40dimforge/rapier3d-compat)). The checkout only contains 0.12.0 transitively under `@types/three`, with a 1.4 MB `rapier_wasm3d_bg.wasm`; that is inventory evidence, not an authorization to rely on the transitive package.

**Fit.** This is the best candidate for a player capsule, step/slope handling, dynamic props, and contact events if Allworld needs physical gameplay. It should own a fixed-step simulation only while the scene is active; render transforms would be copied into the existing avatar/group and camera code. Do not put crowd mannequins, wallet state, or ordinary static scenery into a world by default.

**Exact seam.** Introduce an adapter with `setPosition`, `setDesiredVelocity`, `step(dt)`, `readTransform`, and `readGroundContact`, then call it from the existing `Walker.step()` contract ([movement.ts](/Users/anthonyakpan/Desktop/JoinAllworld/src/scene/movement.ts:143)). Start with streamed street tile solids and a generated neighbourhood ground/collider source; retain `createWalkGrid()` for click/path reachability and use the controller only for continuous displacement, slope/step response, and ground facts. Do not feed the current venue `footprintRecorder` boxes directly as a mesh collider without filtering overhead/camera solids from walkable support. Keep `poseAvatar()`/`SkinnedBody.stride()` as the visual layer. Physics must be disabled when the host is idle, hidden, or in a non-interactive preview so it respects the existing motion-loop battery rule.

**Cost and risk.** WASM initialization, collider authoring, fixed-step accumulation, interpolation, and determinism/version behavior add meaningful complexity. A rigid-body world does not automatically solve animation foot placement or authored interaction anchors. The old JS binding's archive is a maintenance trap; pin and audit the current package.

**Acceptance probe.** One player capsule on a representative Lagos street: walk, jog, stop, step over a curb, descend a ramp, slide along a wall, and recover from a blocked corner. Verify no tunneling, no root/visual drift, no extra idle frames, and that the current camera `resolve()` behavior still keeps the avatar visible. Record WASM cost and frame time on a low-tier mobile profile before considering broader adoption.

**Version/compatibility checkpoint (2026-10-13).** The current npm package is 0.21.0, while the local transitive copy is 0.12.0; Rapier's changelog documents character-controller changes across releases, so an experiment must pin the package and test the exact API rather than infer it from the archived `rapier.js` docs ([current changelog](https://github.com/dimforge/rapier/blob/master/CHANGELOG.md)).

### 2. recast-navigation-js: navmesh paths for streets and NPCs

**Source and license.** `recast-navigation-js` ships ESM for Node and browsers, has core/generator/WASM packages and an optional Three.js integration, and publishes a vanilla Three example ([npm package/readme](https://www.npmjs.com/package/recast-navigation), [repository](https://github.com/isaac-mason/recast-navigation-js)). The JavaScript package is MIT; the underlying Recast & Detour project is Zlib licensed ([upstream license](https://github.com/recastnavigation/recastnavigation)).

**Fit.** This addresses authored walkable routes, NPC path following, and crowd navigation. It is a better match than physics for “walk to venue,” traffic-like pedestrians, and city blocks. It does not replace collision response or animation; combine its path points with the existing movement/stride driver and optionally Rapier later.

**Exact seam.** The current route contract is `WalkGrid.path()` consumed by `Walker.goTo()` ([walk-grid.ts](/Users/anthonyakpan/Desktop/JoinAllworld/src/scene/walk-grid.ts:27), [movement.ts](/Users/anthonyakpan/Desktop/JoinAllworld/src/scene/movement.ts:143)). A navmesh experiment should implement an adapter with `free`, `nearest`, `clearLine`, and `path` semantics, then pass its waypoints through `Walker.setGrid()`/`goTo()` so venue, campus, street, and neighbourhood callers keep one movement contract. Existing callers include streamed street grid rebuilds ([street/host.ts](/Users/anthonyakpan/Desktop/JoinAllworld/src/street/host.ts:94)) and campus routing ([campus/unilag/navigation.ts](/Users/anthonyakpan/Desktop/JoinAllworld/src/campus/unilag/navigation.ts:19)). Peer interpolation and `poseAvatar(..., { pose: 'walk', stride })` remain downstream visuals ([neighbourhood-scene.ts](/Users/anthonyakpan/Desktop/JoinAllworld/src/scene/neighbourhood-scene.ts:168)). Keep dynamic people and interactive props out of the baked mesh; use the existing soft-circle avoidance or a later physics adapter.

**Cost and risk.** WASM and navmesh build memory are additional load; baking from procedural/streamed city assets needs a stable source mesh and versioned parameters (agent radius, height, climb, slope). A navmesh can say a route is walkable while the visual avatar clips a prop unless those source geometries and agent dimensions agree.

**Acceptance probe.** Bake one bounded neighbourhood. Ask for paths between home, street, and three venues; verify no route leaves the walkable surface, arrivals are stable, rerouting works after a blocked target, and the existing idle-to-walking-to-arrived frame-loop assertions remain true. Compare a twelve-NPC route scene against the current peer interpolation for CPU/WASM and memory.

**Version checkpoint (2026-10-13).** The current upstream package metadata reports `recast-navigation` 0.43.1, MIT, ESM, with core/generator dependencies at the same version and Three 0.178 in its development examples ([package metadata](https://raw.githubusercontent.com/isaac-mason/recast-navigation-js/main/packages/recast-navigation/package.json)). Allworld is on Three 0.180.0, so validate the optional Three helper against r180 or use the core/generator packages through the vanilla adapter; do not import the repository's React/React-Three examples.

### 3. Three.js CCDIKSolver: targeted IK without a framework wrapper

**Source and license.** Three.js documents `CCDIKSolver` as an addon for `SkinnedMesh`; it accepts target/effector/link chains, axis and rotation limits, iterations, and blend factors, and updates the bones in place ([official docs](https://threejs.org/docs/pages/CCDIKSolver.html), [source](https://github.com/mrdoob/three.js/blob/master/examples/jsm/animation/CCDIKSolver.js)). Three.js itself is MIT licensed ([license](https://github.com/mrdoob/three.js/blob/dev/LICENSE)). The installed source is exactly Three r180.0 (`node_modules/three/package.json`): `update(globalBlendFactor = 1.0)` calls `updateOne`, and `updateOne` chooses `ik.blendFactor` over the override, then slerps each link back toward its initial quaternion when blend is below 1 ([installed source](/Users/anthonyakpan/Desktop/JoinAllworld/node_modules/three/examples/jsm/animation/CCDIKSolver.js:77)).

**Fit.** This is the lowest-risk animation experiment because the project already has a skinned skeleton, checkpoint/restore ordering, and a two-bone foot solver. Use it for a hand-to-tool reach, a look-at/aim prototype, or a bounded alternative foot chain; do not replace the existing solver until it proves better under the project's clip and wardrobe constraints.

**Exact seam.** Instantiate one solver per loaded body after the skeleton is available. Sample the authored clip, restore the mixer checkpoint as today, call `solver.updateOne(ik, blend)` or `solver.update(blend)`, then run clothing/foot-contact checks and `object.updateWorldMatrix()`. In r180 the solver expects target/effector/link indices into `mesh.skeleton.bones`; it updates matrices internally while iterating, but it does not create a frame loop. Keep all solver calls inside `SkinnedBody.show/stride/step` or a new explicit `solvePose()` method; never let the addon create its own RAF loop.

**Cost and risk.** CCD is iterative and can produce unstable results with bad link ordering, limits, or targets. It is bone-index based, so both body variants need a manifest mapping and acceptance fixtures. It does not provide physics or collision awareness by itself.

**Acceptance probe.** On both shipped body files, solve each foot against a shallow ramp and a one-step height change, with iterations 1/2/4 and blend 0.25/0.5/1.0. Verify ankle orientation, no knee flip, no jitter over repeated samples, and no change to the current resting poses. Then test a hand reach during `cook` or `work` while preserving wardrobe overlays.

## Other useful options and examples

### cannon-es: lightweight JavaScript physics, useful as a comparison

`cannon-es` is a TypeScript-friendly flat ESM/CJS fork of cannon.js with tree-shaking, examples, and an MIT license; current upstream package metadata is version 0.20.0 ([package metadata](https://raw.githubusercontent.com/pmndrs/cannon-es/master/package.json), [repository/readme](https://github.com/pmndrs/cannon-es)). It may be adequate for simple dynamic props or a prototype, but the project itself lists performance enhancements and V-HACD as future work. Treat it as a bounded comparison against Rapier, not the default character-controller choice. The adapter seam would be the same capsule/transform interface above. Do not import `use-cannon` or any React wrapper into this Vue/vanilla engine; use the core package only.

### three-vrm: standards-based humanoid loading and retargeting path

`@pixiv/three-vrm` is a maintained MIT-licensed Three.js library for loading VRM, with VRM loader plugins, humanoid access, expression/spring-bone features, and examples; current upstream package metadata reports 3.5.5 with a `three >=0.137` peer and development dependency on `^0.180.0` ([package metadata](https://raw.githubusercontent.com/pixiv/three-vrm/dev/packages/three-vrm/package.json), [repository/readme](https://github.com/pixiv/three-vrm), [license](https://github.com/pixiv/three-vrm/blob/dev/LICENSE)). This can be a future imported-avatar path or a retargeting boundary, but it should not replace the compact built-in body: VRM assets, materials, spring bones, and package size need separate budgets. Keep `normalizeLook` and wardrobe IDs as the game contract, then map an imported avatar into a renderer adapter that exposes the existing `SkinnedBody` operations.

### VRM ecosystem and asset rights: code license is not model/motion permission

The VRM ecosystem is useful for interoperable humanoid metadata and avatar tooling, but each `.vrm`, texture, motion clip, and creator policy carries its own rights. The `three-vrm` MIT license only covers that library's code; it does not grant rights to redistribute a model or animation loaded through it. Candidate asset intake must record the asset's exact source URL, author, license, attribution text, commercial/derivative terms, and whether motion rights are separate. A model repository being public or its loader being MIT is insufficient evidence for shipping the content.

### Sketchbook: architecture reference, not a dependency

The upstream Sketchbook project is a Three.js/Cannon.js web game-engine example with third-person controls, vehicles, NPCs, a raycast capsule controller, and an explicit movement state machine ([upstream repository](https://github.com/swift502/Sketchbook); see its README and source). Its repository LICENSE is MIT, copyright 2020 swift502 ([license](https://raw.githubusercontent.com/swift502/Sketchbook/master/LICENSE)); that covers code, while any separately included model/motion assets still need their own notices. It is useful for studying capsule/controller state transitions and camera/character separation. Treat its code and assets as a separately audited reference; do not copy its assumptions into Allworld or depend on a React wrapper. Verify the exact upstream commit and asset notices before any reuse.

### Existing Three.js animation utilities

Before adding another animation framework, use Three's existing `AnimationMixer`, `AnimationClip`, GLTF loader, and `CCDIKSolver` primitives. Allworld already has clip sampling and explicit bounded transitions ([skinned.ts](/Users/anthonyakpan/Desktop/JoinAllworld/src/scene/body/skinned.ts:194), [poses.ts](/Users/anthonyakpan/Desktop/JoinAllworld/src/scene/body/poses.ts:5)). Any new utility must preserve the rule that a still pose is sampled once and only bounded transitions run over time.

## Keep, replace, and sequencing decisions

Keep the procedural avatar and its deterministic look normalization for crowds, low-tier devices, fallback rendering, and any offline-safe scene. Keep the current GLB body/clip pack, wardrobe renderer, animation checkpoint, foot-contact solver, and demand-driven motion loop. Keep the box-based camera occluder until a measured need for mesh/physics queries exists.

Add recast-navigation-js first for one bounded neighbourhood if NPC routing is the immediate gameplay gap, but adapt the existing `WalkGrid`/`Walker` contract rather than bypassing it. Add Rapier only behind a narrow controller adapter after the capsule probe demonstrates a user-visible improvement over current movement; start with street/neighbourhood terrain because venue and home already have rendered support sampling. Add CCDIKSolver as an isolated skinned-body experiment for a concrete reach/foot problem. Consider three-vrm only for an explicitly scoped imported-avatar feature, with asset rights and download budgets approved per asset.

Do not replace `characters.ts`, introduce a React renderer/wrapper, or make a physics world the source of truth for economy, interaction receipts, or server-only living-world actions. Physics and navigation should produce movement/pose facts; the game systems remain authoritative for gameplay state.
