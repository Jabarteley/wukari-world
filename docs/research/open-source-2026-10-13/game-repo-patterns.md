# Open game-repo patterns for Allworld

Checked 2026-10-13. These are four actual upstream games/demos, pinned to the commits below. The goal is to borrow boundaries and tests of ideas, not to transplant engines, network protocols, or art. Code licenses do not grant rights to the repositories' models, textures, sounds, or third-party dependencies; audit each asset separately before reuse.

## Veloren: typed social actions with server checks

At the pin, `common/src/comp/controller.rs` defines serializable `ControlEvent` variants such as `Interact(Uid)`, `Mount(Uid)`, `Dialogue`, trade actions and inventory events ([source](https://github.com/veloren/veloren/blob/40d3c27ec8b1280e6c32c568cbc3339901530f6a/common/src/comp/controller.rs)). The server interaction system handles events after checking entity state, positions and eligibility; for example, NPC interaction checks distance and target state before queueing a talk event, while dialogue checks actor status, client/NPC constraints and range before item exchange ([source](https://github.com/veloren/veloren/blob/40d3c27ec8b1280e6c32c568cbc3339901530f6a/server/src/events/interaction.rs)). Its typed interaction link also prevents self-interaction, limits one active interaction, checks range and target conditions, and persists the link while both entities remain valid ([source](https://github.com/veloren/veloren/blob/40d3c27ec8b1280e6c32c568cbc3339901530f6a/common/src/interaction.rs)).

Transferable pattern: model an interaction as a typed request plus a server-side eligibility predicate plus a persisted active state. The Allworld seam is the existing action registry and server checks behind venue-world actions, street `enter`, campus shuttle `board`, and merchant flows. Client proximity and collision can improve affordances, but the action handler must re-check identity, venue, range, inventory and settlement state. A small first application would be a Lagos vendor conversation or “inspect stall” action with a typed target id and a short buildup state; it should not import Veloren ECS or copy its UI/assets.

Acceptance probe: replay a valid request, an out-of-range request, a request against a missing target, and a duplicate request. The server should produce one accepted action or one explicit rejection and one economic receipt at most. This is a proposed probe, not a claim that current Allworld actions already have Veloren’s interaction-link semantics.

## SuperTuxKart: simulation order and vehicle authority

The pinned `doc/physics_order` is unusually concrete: a frame determines the simulation interval, records input/network events, applies controls, updates speed/slipstream and vehicle forces, then advances Bullet physics; the network protocol and world time update follow the physics step ([source](https://github.com/supertuxkart/stk-code/blob/fb03fce68cec87322d89f2526c37a4fc90fc6407/doc/physics_order)). The vehicle implementation separates chassis, wheel raycasts, suspension and wheel transforms (`src/physics/btKart.cpp`, [source](https://github.com/supertuxkart/stk-code/blob/fb03fce68cec87322d89f2526c37a4fc90fc6407/src/physics/btKart.cpp)); the repository also carries kinematic character and vehicle primitives in its Bullet subtree, which are upstream dependencies rather than Allworld-ready modules.

Transferable pattern: write the order contract before adding motion. For Allworld, input intent, accepted journey/action state, visual controller, physics/collision experiment, and render interpolation need named phases. This directly complements the physics contract: a client-local experiment may show a better vehicle or boarding approach, but server `activeAction`, fare debit, destination and completion remain authoritative. The campus shuttle’s current route/time pose in `src/campus/unilag/shuttle.ts` should remain the source of truth until a server simulation is intentionally designed.

Acceptance probe: record one fixed-step trace containing input, accepted server state, controller output, resolved collision output and rendered transform. Replaying the same trace should produce the same action requests and no duplicate fare. Do not use visual smoothness as evidence of network determinism.

## Luanti: bounded movement integration over streamed geometry

At the pinned commit, `ClientEnvironment::step` caps large elapsed time, computes a bounded increment based on player speed, subdivides the frame into steps, applies controls and gravity/liquid rules, then calls local-player collision movement for each increment ([source](https://github.com/luanti-org/luanti/blob/5bb520ba544536c4c2914bc0a5ad386e758d7036/src/client/clientenvironment.cpp)). `LocalPlayer::updateSneakNode` derives a valid support node from map collision boxes and checks the player’s clearance above it ([source](https://github.com/luanti-org/luanti/blob/5bb520ba544536c4c2914bc0a5ad386e758d7036/src/client/localplayer.cpp)).

Transferable pattern: keep movement substepping and support detection adjacent to the streamed geometry authority. For Allworld, street tile data and venue footprint data should feed any future collider/support cache; rendered meshes should not be sampled as an accidental second source. This supports the existing `createWalkGrid`, `footprintRecorder`, `tileGroundAt`, and venue `contactHeightAt` seams. It does not justify replacing the current grid with a voxel or node system.

Acceptance probe: feed a synthetic raised curb and a large frame delta into an offline movement fixture. Assert that the maximum per-substep translation is bounded, support state is stable at rest, and the renderer receives the same accepted location after a tile/venue source refresh. The thresholds are proposed fixture values, not Luanti-derived measurements.

## Wave Riders: sampled environment physics and camera readability

The pinned MIT demo’s `BoatPhysics.js` explicitly defines metres, seconds and kilograms, uses multiple hull buoyancy points sampled against the sea, applies spring/damper lift, stern thrust, steering torque and lateral drag, and caps/assists roll ([source](https://github.com/developmentation/wave-riders/blob/5d9e28bcb14d9e0d08845e15af8bfce61fad4d29/src/game/BoatPhysics.js)). `FollowCamera.js` follows the hull with critically damped position/orientation, looks ahead of the bow, scales distance and height with speed and wave height, and clamps the lens above the sampled sea surface ([source](https://github.com/developmentation/wave-riders/blob/5d9e28bcb14d9e0d08845e15af8bfce61fad4d29/src/game/FollowCamera.js)).

Transferable pattern: keep an environment sampler as an explicit interface (`heightAt(x,z)` plus optional normal/current data), and let both the vehicle and camera consume it. The Allworld seam is a future water/littoral feature module beside `src/street` and venue scenes, with a local sampled water surface and Three.js presentation. The camera idea is more immediately useful: speed-aware follow distance, look-ahead and a hard surface floor could improve boat, shuttle or neighbourhood cameras without changing player/network authority. Do not copy the demo’s boat parameters into Allworld’s `0.72` street scale; define a per-feature unit contract first.

Acceptance probe: on a fixed sampled-water fixture, compare hull roll/pitch and camera clearance at rest, acceleration, turning and wave crest. Assert that the camera never crosses the sampled surface and that economic/action state is unchanged by physics outcomes.

## Strongest recommendations for Allworld

1. **Use Veloren’s typed-request/check/persist pattern for social interaction design.** Keep Allworld’s existing server action registry and settlement boundaries; add explicit target/range/eligibility states where a feature needs them. This is the strongest direct social-game transfer.
2. **Use SuperTuxKart’s phase-order document for any future vehicle or physical boarding experiment.** It gives a reviewable input → simulation → network → presentation order without asking Allworld to adopt Bullet or replace the shuttle’s authoritative route.
3. **Use Luanti’s bounded-substep/support approach to harden streamed-scene movement fixtures.** This is a pattern for source geometry and time handling, not a recommendation to add a voxel engine.
4. **Use Wave Riders as the concrete Three.js water/camera prototype reference.** Isolate it behind a feature seam, pin the MIT code separately, and clear every model/audio/texture license independently.

No repository here is a drop-in replacement for Allworld’s engine or network authority. The next implementation decision should follow a focused fixture and source/license review, not repository popularity or a visual demo alone.
