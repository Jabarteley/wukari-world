# Physics adoption contract for Allworld

Checked 2026-10-13. This is a bounded adoption contract, not a physics implementation. It preserves the current custom walker as the rollback path and defines one measurable experiment before any runtime dependency or gameplay-authority change.

## Current authority and seams

The current player controller is deterministic arithmetic in `src/scene/movement.ts`: `Walker.step(dt, cameraYaw, snap)` advances a fixed-speed avatar over an occupancy grid, follows A* waypoints, slides around rectangles/circles, applies soft crowd avoidance, and turns toward travel at `TURN_RATE = 14` radians/second (`src/scene/movement.ts:1-29,39-49,143-195`). The grid is generated from a scene description and from `footprintRecorder`, which records the same primitive footprints that the venue draws (`src/scene/movement.ts:6-16,51-63,80-133`; `src/scene/walk-grid.ts`). This is the current movement authority for venue and campus walking. It is not a deployment guarantee: deterministic arithmetic alone does not establish network agreement, collision parity, or economic correctness.

The street host scales the walker speeds by `0.72`, builds the avatar at `scale: 0.72`, and places its rendered body at `y = 0` (`src/street/host.ts:40,145,170-174`). Street rendering is ground-at-zero tile geometry, while `createStreetRenderer().grid()` makes a 384×384, two-metre-cell walk grid from `tileGroundAt` (`src/street/renderer.ts:71-86`). `STREET_NETWORK_SCALE` is a separate neighbourhood-space conversion (`src/game/neighbourhood-space.ts:1-5`); it should not be silently reused as a physics conversion without an explicit scene-space contract.

The client sends rounded street positions to the server (`src/street/client.ts:42-50`). A proposed physics controller therefore cannot be treated as a second accepted-position authority: it must either remain a local presentation/controller whose result is reconciled to `client.move`, or the server must reproduce the same fixed-step collision inputs and rules. The venue experiment below has a separate local/server action path and does not reuse street reconciliation.

Vehicle movement is not currently rigid-body movement. UNILAG shuttle routes are built from fixed road points and `shuttlePose()` derives a position from server time/progress with `y: 0` (`src/campus/unilag/shuttle.ts:183-218,221-260`). Boarding validates venue, stop, route and fare, then debits and stores the active server action (`src/campus/unilag/shuttle.ts:263-282`); completion updates the destination and ride count (`src/campus/unilag/shuttle.ts:285-309`). Physics contact can improve approach and presentation, but it cannot prove boarding, payment, fare, destination, or any other economic fact.

The scene frame loop intentionally stops on idle and on hidden tabs (`src/scene/motion-loop.ts:1-20,44-75`; `src/street/host.ts:146-158`). That is safe for the current visual-only walker. It is not a safe blanket rule for a future physics world: an awake dynamic body, moving platform, or unresolved contact must continue stepping, or be explicitly paused and resumed from an authoritative state.

## Candidates against this contract

| Candidate | Pinned API/compatibility evidence | Fit here | Decision |
|---|---|---|---|
| Current custom controller | Local `Walker` API and grid seams above | Lowest cost, already owns exact arrival, hops, door approach and server reconciliation; it has no general collision manifold, slope, platform or dynamic-body semantics | **Keep as baseline and rollback** |
| Rapier 3D kinematic character controller | The current JavaScript guide creates a controller with `world.createCharacterController(offset)`, calls `computeColliderMovement(collider, desiredTranslation)`, then applies `computedMovement()` to a collider or kinematic body. It documents capsule suitability, slope limits, autostep, snap-to-ground, collision reports, filters and optional impulses to dynamic bodies: [setup](https://rapier.rs/docs/user_guides/javascript/character_controller_setup/), [controller](https://rapier.rs/docs/user_guides/javascript/character_controller/). The current package page is [@dimforge/rapier3d-compat](https://www.npmjs.com/package/@dimforge/rapier3d-compat); the checked package was 0.21.0 on 2026-10-13. The old [rapier.js repository](https://github.com/dimforge/rapier.js) is archived and its changelog records the 2025 package migration to Rapier 0.24 and separate deterministic flavors; pin a package/version in implementation work rather than copying an old example. | Closest collision fit, but there is adapter cost: `Walker.step` currently mutates `walker.x/z` and fires `arrive` while consuming a route (`src/scene/movement.ts:337-361`), so it exposes no pure desired-translation proposal. A safe production adapter must split proposal → Rapier-resolved movement → verified arrival, or use an isolated fixture input path; calling `Walker.step` first cannot preserve callback truth after Rapier correction. Requires collider authoring, WASM lifecycle, fixed stepping, platform rules and reconciliation. | **Strongest first experiment** |
| Rapier dynamic capsule | Rapier supports dynamic rigid bodies, but the character-controller guide makes the controller-to-collider/kinematic-body distinction explicit and says gravity is supplied by the caller ([guide](https://rapier.rs/docs/user_guides/javascript/character_controller/)). | Better physical pushing/ragdoll interaction, but transfers locomotion, grounding, sleeping, impulses and network correction into a much larger authority problem. It would also conflict with exact `Walker.goTo({ exact, via, arrive })` semantics until those are redesigned. | **Do not make the first player controller**; consider later for explicitly physical NPCs/props |
| cannon-es | Official docs expose `World.step(dt, timeSinceLastCalled?, maxSubSteps?)` for fixed stepping/interpolation ([World](https://pmndrs.github.io/cannon-es/docs/classes/World.html)); `Body` exposes dynamic/kinematic/static types and configurable sleep state/time ([Body](https://pmndrs.github.io/cannon-es/docs/classes/Body.html)). The official package metadata is [MIT, cannon-es 0.20.0](https://raw.githubusercontent.com/pmndrs/cannon-es/master/package.json), checked 2026-10-13. | Viable for a small dynamic-prop sandbox, but it has no equivalent built-in Rapier character-controller seam in the cited API. A player would need custom capsule motor, stair/slope rules, collision filtering and reconciliation. | **Use only if a later prop/vehicle prototype specifically needs cannon’s existing examples; do not add as a parallel player stack** |

Rapier is not automatically deterministic across a network merely because its local step is fixed. A server/client agreement would require a pinned engine flavor, identical collider geometry, fixed timestep, input ordering, floating-point/runtime assumptions and reconciliation policy. For the first experiment, physics is deliberately client-local and gameplay remains server-authoritative.

## Units and body contract

The code describes a 2.45-unit avatar as an approximately 1.75 m person before scene scale (`src/scene/movement.ts:39-44`). The street host’s `0.72` visual scale implies a proposed street body height of roughly `2.45 × 0.72 = 1.764` scene units. The current grid’s venue defaults are `CELL = 0.4` and `AVATAR_RADIUS = 0.34`, while street explicitly uses `cell: 2, radius: 0` (`src/scene/walk-grid.ts`; `src/street/renderer.ts:82-85`). These are different authored scales, so the experiment must not infer a collider radius from a renderer mesh.

**Proposed collider starting values (to be measured in the fixture, not treated as shipped constants):** street capsule radius `0.245` scene units (`0.34 × 0.72`), total height `1.764`, and a capsule half-height of approximately `0.637` if the engine’s capsule convention is total height `2 × halfHeight + 2 × radius`. Use a small controller offset such as `0.01` only after confirming it in the pinned Rapier API; the official guide describes the offset as a required numerical-stability gap ([offset and setup](https://rapier.rs/docs/user_guides/javascript/character_controller/)). Record the exact chosen dimensions, up vector, maximum climb slope, autostep height/width and snap distance with the fixture so a later server implementation has an auditable contract.

The rendered body and foot IK remain presentation. `src/scene/body/foot-contact.ts` caps foot correction at `0.12` source body metres and does not move the root; it cannot substitute for capsule grounding. A physics collider should be centered from the existing avatar anchor and the visual rig offset should be measured once, then kept separate from gameplay position.

## Static geometry, platforms and sleep

Static colliders must be authored from the same validated source that currently produces walkability: venue `footprintRecorder` shapes, `walk` descriptions, street tile ground/road/building data, and campus zone data. Do not crawl rendered triangles at runtime. Each collider batch should retain a source kind, scene-space transform, source hash/version, and whether it is ground, blocking solid, trigger, or decorative. The renderer can continue to stream/evict tiles; collider lifetime must follow the same resident tile/scene lifetime.

Moving platforms are not static colliders. A platform must be a kinematic body whose authoritative transform is sampled at fixed-step boundaries; the previous/current transform supplies platform delta or velocity to the player controller. On eviction or action transition, detach the player by an explicit rule and reconcile to the server anchor. The shuttle remains the fixed route/time presentation described above; it is not converted to a physics-owned vehicle by this contract.

Dynamic props may sleep. They must be configured with an explicit sleep threshold/time and wake on input, contact, platform motion or scene re-entry. The world must not stop merely because player input is idle while any relevant dynamic body is awake or a kinematic platform is moving. A scene may stop rendering when all physics bodies are static/sleeping and no visual easing remains; it must not silently freeze an awake object. cannon-es documents `allowSleep`, `sleepSpeedLimit`, `sleepTimeLimit`, `sleep()` and `wakeUp()` ([World](https://pmndrs.github.io/cannon-es/docs/classes/World.html), [Body](https://pmndrs.github.io/cannon-es/docs/classes/Body.html)); the equivalent Rapier sleep policy must be recorded during implementation.

## Fixed-step and lifecycle contract

The experiment uses a fixed physics step, proposed `1/60` second. On each visible RAF callback: clamp frame elapsed time (proposed maximum `0.05` s), add it to an accumulator, run up to a proposed four fixed substeps, and retain the remainder for interpolation. Render transforms from previous/current physics state with `alpha = accumulator / fixedDt`. If the cap is reached, emit a diagnostic and choose an explicit catch-up/resync policy; never turn a long frame into one variable-sized physics step. This follows Rapier’s fixed-`dt` accumulator guidance ([integration parameters](https://rapier.rs/docs/user_guides/c/integration_parameters/)) and is compatible with cannon-es’s `World.step` fixed-step/interpolation overload ([World](https://pmndrs.github.io/cannon-es/docs/classes/World.html)). The four-substep cap is a proposed acceptance parameter, not a measured budget.

Rapier WASM should initialize once per scene chunk, await readiness before creating colliders, and expose a load-failure fallback to the current `Walker`. The `-compat` package is the bundler-friendly option but carries a materially larger embedded-WASM payload than a normal external-WASM path; capture the actual production bundle size before choosing it. On scene disposal, remove character controllers, colliders, rigid bodies and the world, stop pending stepping, and release scene references. Do not put WASM initialization in a frame callback or create one world per avatar.

Hidden-tab policy must be explicit. Current hosts clear held input, stop the loop and send a street position when hidden (`src/street/host.ts:146-158`). For a physics experiment with no server-owned dynamic object, pause at a fixed-step boundary, store the last accepted state, and on visibility restore discard stale wall time and reconcile to the server before waking. If an awake object or moving platform has gameplay consequences, either keep a server/headless simulation authoritative or mark the scene unavailable until a fresh authoritative snapshot arrives. Never advance a hidden tab by an unbounded elapsed delta.

## Smallest experiment: raised approach at one existing venue

Use one existing venue that already declares a raised stage/deck/approach in its scene data. The venue currently has an explicit distinction between walkable floor, an approach point and a short hop (`src/scene/movement.ts:18-29`), and venue contact sampling can inspect raised support (`src/scene/venue-scenes.ts:916-955`). Build one opt-in experiment scene layer with:

1. the existing venue static footprint colliders plus one authored low step/raised platform from the same scene-space dimensions;
2. one Rapier kinematic capsule driven by an isolated copy of the venue input/path intent, with no dynamic props in the first pass;
3. the existing visual avatar and foot/stride code, with arrival determined only after the resolved capsule reaches the validated interaction point;
4. a door/seat or venue action at the top of the raised surface, still gated by the existing server action; and
5. a feature flag that switches this offline fixture between current custom movement and Rapier-resolved movement. Do not route the venue result through street `client.move`: venue actions have their own authority path.

This tests a concrete gameplay feature—walking from the floor to an elevated venue interaction point—without pretending that physics owns fare, inventory, entry, or the campus shuttle. It also isolates the current custom controller’s hop semantics from Rapier autostep/snap-to-ground. Do not add a dynamic capsule or physical vehicle until this kinematic comparison passes.

## Proposed acceptance targets

These are targets for the experiment, not current measurements:

- **Authority:** 100% of successful venue actions still arrive through the existing server action; physics alone can never trigger payment, boarding, or inventory proof. A server correction must move the local capsule to the accepted point within one reconciliation cycle.
- **Geometry:** on 100 repeated floor-to-platform and platform-to-floor traversals at 30, 60 and 120 RAF Hz, the capsule never tunnels through the authored step, never climbs a step above the configured autostep height, and reports grounded at rest. Record maximum horizontal and vertical error against the authored fixture; proposed pass bound is `≤ 0.05` scene units.
- **Path seam:** the same authored approach point and validated arrival condition succeed under both feature-flag modes. Because `Walker.step` currently owns route mutation and callback firing, a production adapter must first introduce a proposal/resolution/verified-arrival seam; the offline fixture must not claim that this seam already exists. No street `client.move` reconciliation claim is made for this venue experiment.
- **Rendering:** after stopping input, the capsule and visual rig settle without a root snap; the rig’s existing foot solver may correct only within its source cap. Measure proposed p95 controller-to-render transform discrepancy `≤ 0.03` scene units after one fixed step.
- **Timing:** with the existing-style proposed `maxFrameDt = 0.05` s and `fixedDt = 1/60` s, a forced 250 ms RAF stall is clamped to at most three substeps; the discarded 200 ms is reported as dropped wall time and never becomes one 250 ms collision step. The proposed four-substep cap still applies to accumulated backlog if the implementation permits it; acceptance must record both `substeps` and `droppedTime` rather than claiming that this particular stall reaches four steps. At ordinary frames, simulated time advances only in `1/60` increments.
- **Idle/sleep:** with no dynamic bodies, the loop may stop once the capsule is stationary and the camera has settled. Add one optional awake dynamic test prop only in a follow-up; then prove the loop continues until the prop sleeps, and wakes after contact/input.
- **Visibility:** hide for at least one second during approach, restore, reconcile to the server, and resume without a large teleport caused by hidden wall time. If an awake gameplay body is introduced, the experiment must show its explicit server snapshot/pause policy.
- **Performance:** profile the one venue with the current three.js render diagnostics and physics step count. Proposed budget is no more than 4 fixed substeps per RAF and no more than 2 ms p95 physics time on the project’s reference desktop; measure before using this as a release gate.

## Keep/replace decision and risks

Keep `Walker`, `WalkGrid`, footprint recording, exact approach/arrival semantics, street client/server reconciliation and shuttle route/action code. Replace only the collision-resolution step inside the opt-in fixture if Rapier proves the raised approach materially better. Do not replace `createWalkGrid` with a physics mesh in this first experiment: the grid still owns path planning and current server-facing reachability, while the collider set is a derived local obstacle representation.

Rapier kinematic is the recommended next experiment because it supplies the missing capsule/step/slope/ground collision seam with a documented API while preserving the current movement authority. A dynamic capsule is deferred because it would introduce sleep, impulse, gravity, network correction and action-approach redesign at once. cannon-es remains a reasonable MIT-licensed prop sandbox, but adopting it for player locomotion would create a second custom character controller and duplicate lifecycle/authority work. The largest unresolved risks are authored collider parity with streamed street/venue geometry, hidden-tab reconciliation, WASM payload/lifecycle, and whether a later server needs to reproduce physical movement. None is solved by adding a client physics package.
