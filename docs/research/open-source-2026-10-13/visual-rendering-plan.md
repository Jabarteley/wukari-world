| Day/night | `src/map3d/city-build.ts:153-157` already has day/dusk/night sky, hemisphere, sun, water, windows, waves, and shadow presets. `src/scene/lighting.ts:19-35` has venue presets. | Improve the authored Lagos palette and atmosphere before adding screen-space effects. |
| Textures/materials | `src/map3d/city-build.ts:290` and `src/scene/models/gltf-source.ts:44-51` mark color textures `SRGBColorSpace`; `src/scene/kit.ts:50-58` uses Standard materials by default and Lambert only under the explicit matte flag. | Color management is mostly in the correct linear-working/sRGB-output direction. A PMREM environment would affect Standard materials, not Lambert scenery. |
| Post effects/environment | Repository search found no `PMREMGenerator`, `scene.environment`, `EffectComposer`, or AO setup in the reviewed scene/map paths. | These are candidates, not existing features; they need opt-in benchmarking and a fallback path. |

Three.js’ color-management guidance says scene operations use linear-sRGB and display output should be sRGB; the current renderer settings and sRGB atlas assignments follow that model ([Three.js color-management manual](https://threejs.org/manual/pages/color-management.html)). Keep hex authored colors as sRGB inputs and light intensities as scene values. Do not apply a second gamma pass. If postprocessing is introduced, preserve `outputColorSpace = SRGBColorSpace`; the postprocessing project documents that workflow ([postprocessing output color space](https://github.com/pmndrs/postprocessing#output-color-space)).

One concrete seam is the map’s `ACESFilmicToneMapping`/`1.08` versus the shared `NeutralToneMapping`/`1` (`src/map3d/map3d.ts:158-161` versus `src/scene/look.ts:61-70`). This is a consistency candidate, not an automatic “fix”: capture the same Lagos venue/map palette under both settings and choose by legibility of roads, water, skin, and cream walls.

## Three visual presets

| Preset | Scope and implementation shape | Expected visual result | Cost/risk and gate |
|---|---|---|---|
| **1. Lagos daylight clarity (phone + wide)** | Keep existing tiers, authored shadows, Standard/Lambert split, and one-pass render. Tune `CITY_LIGHT.day` and venue outdoor colors together; optionally add low-density `Fog`/`FogExp2` to the map only after testing clear-label readability. | Better separation between sand, asphalt, water, cream walls, and skin without changing the art language. A light horizon haze can make the large map feel atmospheric. | Fog changes distant color and can reduce map-label contrast; no extra fullscreen pass, but it must be checked at neighborhood zoom and on low-end phones. Adopt first if visual comparison passes. |
| **2. Warm dusk atmosphere (wide first, phone-safe fallback)** | Reuse existing dusk presets, warm window emissive colors, and authored sky. If the result needs roughness-dependent highlights, generate one small environment from a scene/equirectangular source with `PMREMGenerator`; keep it off on phone tier. Three.js documents `fromScene`, `fromEquirectangular`, and the extra filtered roughness levels ([PMREMGenerator](https://threejs.org/docs/pages/PMREMGenerator.html)). | More convincing wet-water/painted-metal gradients and a recognisable Lagos sunset while preserving the stylized palette. | PMREM allocates an environment render target and performs prefilter work at startup; it is useful when several Standard materials visibly benefit, not for a single decorative atlas. Gate on first usable frame, visual roughness response, and measured texture allocation—not a claimed FPS number. |
| **3. Hero camera depth (wide/desktop opt-in)** | Add a `postprocessing` `EffectComposer` with one `RenderPass` and one SSAO effect, or a narrowly scoped contact-shadow pass; keep existing map quads and venue shadow maps as the baseline. The library’s vanilla API is `EffectComposer` + `RenderPass` + `EffectPass`, independent of Vue/React ([pinned project README](https://github.com/pmndrs/postprocessing/tree/9cf03cff26615636a564d8bfddf765edb8917441)). | Stronger foot-to-ground and building-to-ground separation for a hero venue/map shot. SSAO gives local crevice depth; a soft authored disc remains cleaner for the deliberately graphic city style. | Fullscreen depth/normal work, extra render targets, shader compilation, and halos/over-darkening are possible. Keep it off phone/data-saver paths until measured. Compare against the existing shadow quad; accept only if it improves recognition without obscuring labels or skin. |

The pinned postprocessing `6.39.5` package is Zlib-licensed and declares `three: ">= 0.168.0 < 0.187.0"` as a peer dependency; its README also describes pass merging and fullscreen effects ([license and peer dependency](https://github.com/pmndrs/postprocessing/blob/9cf03cff26615636a564d8bfddf765edb8917441/LICENSE.md), [package metadata](https://github.com/pmndrs/postprocessing/blob/9cf03cff26615636a564d8bfddf765edb8917441/package.json)). ## Contact shadows, AO, and atmosphere choice

Allworld already has two different contact treatments: venue shadow maps (`src/venue-world.ts:306-317`) and map shadow quads (`src/map3d/city-build.ts:340-369`). A stylized, camera-facing/grounded disc is predictable, cheap, and consistent with the map’s flat language. SSAO is view-dependent and can add depth around curbs and feet, but it can also darken pale Lagos surfaces and introduce screen-edge/halo artifacts. Treat it as a hero preset, not a replacement for authored shadows. Fog or a graded sky is the lower-risk atmosphere lever because it adds depth without another fullscreen effect; test label contrast and water color at neighborhood zoom.

## KTX2 decision boundary

The existing deterministic body pipeline already uses `gltfpack 1.3.0`, meshopt compression, and a 1024px JPEG atlas (`docs/ASSETS.md:63-84`); it explicitly says that gltfpack 1.3 has no WebP/KTX2 output (`docs/ASSETS.md:78`). The inspected male atlas is 81,198 bytes (female 80,164; shops 95,937; home atlas 138,566), all 1024px source images. Do not add a duplicate optimizer or convert one 80k JPEG speculatively.

KTX2 can reduce GPU texture memory when transcoded to a device-native compressed format, but Three’s `KTX2Loader` requires a transcoder path, renderer capability detection before loading, and asynchronous initialization ([r180 loader source](https://github.com/mrdoob/three.js/blob/r180/examples/jsm/loaders/KTX2Loader.js), [KTX2Loader API](https://threejs.org/docs/pages/KTX2Loader.html)). For one roughly 80k transfer, decoder startup/worker setup can exceed the transfer saving; that is an expected startup tradeoff, not a measurement. Memory benefit is a separate question. Consider KTX2 only for a repeated/larger atlas set after measuring: download bytes, decoder/first-visible time, `renderer.info.memory.textures` (a texture-object count, not GPU bytes), estimated decoded/compressed bytes from dimensions, format, and mip levels, device-reported GPU memory where available, and JPEG/KTX2 visual parity. Preserve JPEG fallback.

## Non-invasive acceptance plan

1. Capture a fixed Lagos venue and map fixture at day, dusk, and night with the current render diagnostics (`src/venue-world.ts:1548` exposes draw calls, triangles, geometry/texture object counts, tier, pixel ratio, and shadow map size; these counters are not GPU-byte measurements).
2. Compare preset 1 before/after with identical camera, device tier, and canvas size. Record label contrast, water/road separation, skin readability, and whether distant map features remain legible.
3. On a wide fixture only, prototype PMREM and one AO/contact-shadow option behind a local, reversible flag. Record first usable frame, shader/texture initialization, `renderer.info` object counts (not byte memory), estimated texture bytes from dimensions/format/mips, device-reported memory where available, and screenshots; no FPS claim without repeatable device measurements.
4. If testing KTX2, use at least the male/female/shops/home atlases as a set, warm-cache and cold-cache runs, and the existing JPEG fallback. Stop if transfer savings do not justify startup or if visual parity fails.
5. Keep phone tier one-pass and authored-shadow based unless evidence shows a specific readability regression. Any postprocessing package must be pinned and its peer range tested against the lockfile’s Three `0.180.0`.

Limitations: this note is source inspection and documentation research only. No browser capture, package install, benchmark, shader compilation, or device GPU measurement was performed, so all cost language above is an expected tradeoff and requires the acceptance plan’s evidence.
