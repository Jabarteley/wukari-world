## Runtime state, reset keys, claims, and persistence

The authoritative path is server settlement. `server/life-service.ts:104-150` loads or creates one city life, rebuilds/sanitizes it, advances elapsed time, updates `state.t`, writes the city record back into the session, and retains a per-life salt beside the state. Actions then dispatch against that settled object (`server/life-service.ts:153-182`). This means daily and weekly progression must use Lagos clock keys, not browser time or page visits. The Node store is transactional: `server/store.ts:12-21` documents copy-on-write transactions where rejected promises have no effect; durable transactions are written before resolution, while lazy writes are explicitly weaker (`:42-55`). This is the reuse seam for chapter progress and project contributions.

Mission daily/week roll, wish rerolls, table paid wins/bot credits, gig count, event spraying, family/social interaction counters, and campus weekly/daily records all have explicit keys. Claim accounting is strongest in missions (`claimed`, `sets.day/week`, wallet ledger) and growth table/referral routes (server claim before durable response). A future story/project reward should copy this shape: stable id, period or chapter key, claimed/completed marker, wallet effect reason, and exact retry identity.

## Key gaps and opportunities

1. **No authored branching progression chapter.** Goals/dreams and home scenes exist, but the bounded source lacks a reusable named-story chapter/choice/outcome model for “Hostel Hustle” (`src/game/systems/stories.ts:23-89`). Add one small story slice with chapter id, selected ambition, choice ids, and durable outcome tags; keep content data separate from reducer logic.
2. **Completed but unclaimed missions lapse at period roll.** `src/game/systems/missions.ts:100-114` replaces the daily or weekly set when the Lagos day/week key changes; `:166-183` marks `claimed` and increments lifetime accounting only at claim time. A player can therefore reach `done` and lose the old entry's claimability at the boundary. Preserve or explicitly settle completed-but-unclaimed entries, and expose the rollover rule in the UI.
3. **Campus progression is mechanically rich but narratively unowned.** UNILAG already has exact admission, semesters, hostel, jobs, clubs, discoveries, events, and Whot tables. A story can enter at `status: none`, `admitted`, or `studying` without duplicating requirements.
4. **Meaningful choice seams already exist.** Career dilemmas persist `memory` tags and social NPCs recall deeds; use those tags to make “work/study/help” affect later dialogue, referrals, or event access instead of inventing a second relationship system.
5. **Community event attendance is mostly a counter.** Calendar events and campus events are visible and mission-counted, but normal events have no lasting venue result. A first project should write a bounded shared outcome and expose it in the existing event/campus summary.
6. **Campus contribution is under-modelled.** The shared 200 goal counts volunteered players, not contribution types, progress stages, or a visible completed artefact. A project can extend this existing scan while preserving one contribution per player/day.
7. **Retention telemetry conflates mission completion and claiming.** `src/app/features/growth/MissionsApp.vue:50-56` emits `mission_completed` only after `missions.claim` succeeds, and the catalogue describes it as a finished mission being collected (`src/telemetry/events.ts:90-94`). There is no source event separating progress reached, reward claimed, or completed-but-lapsed. Add distinct completion and claim/lapse events, alongside story/project funnel events; keep values as short ids.
8. **Balance is source-documented, not freshly measured here.** The gig comment records a previous simulator result, but no current 1/7/30-day run was performed. Before changing rewards, run the existing simulator and compare wages, gigs, hunt, tables, referrals, missions, rent, homes, and cars.
9. **Early rewards are cash-heavy.** The ten-goal starter chain totals ₦10,000 (₦500 + ₦500 + ₦1,000 + ₦500 + ₦500 + ₦1,000 + ₦1,000 + ₦1,500 + ₦1,500 + ₦2,000; `src/game/content/goals.ts:30-55`); daily/weekly missions can total ₦8,250 per week (7 × ₦750 daily plus ₦3,000 weekly; `src/game/content/missions.ts:27-35`). Consider story rewards in reputation, relationship tags, cosmetics, access, or a commemorative item, with cash reserved for demonstrated costs.
10. **Agent provenance must stay out of human retention metrics.** The growth route's `session.agent?.char === true` guard is narrower than “all automated own-character actions” (`server/routes/growth.ts:95-100`). New story/project telemetry and shared leaderboards should carry the explicit public-mark and ranking-week family fields described in `docs/AGENTS.md:20-26`, `:114-116`, or explicitly omit agent-originated actions.
11. **No general progression badge catalogue.** Existing location badges and mission titles have different semantics. If a “Hostel Hustle” completion mark is desired, define it as a durable story achievement and a UI projection rather than overloading residence badges.
12. **Offline/reconnect behavior is structurally supported but story-specific proof is absent.** Server settlement and durable state support reload-safe progress, while active timed actions are sanitized. The new story must make each transition idempotent and verify reconnect at chapter boundaries.
13. **No broad social-project search hit.** Do not assume a hidden project API. Design the first project around the existing campus route/store and one bounded content definition; defer a general editor.

## Reuse seams for a smallest first release

1. **Registry events and system slices.** `src/game/systems/goals.ts:491-500` shows the established pattern: persistent slice, event listeners, `advance`, sanitizer, and view. The existing authored home-scene runner also provides draft/publication/run validation (`src/game/systems/stories.ts:23-89`), but not branching campus progression. A story system can listen to `life.started`, `job.applied`, `shift.completed`, `friend.made`, `table.played`, and `campus.*` without coupling campus reducers to story copy.
2. **Campus student reducer and view.** `src/campus/unilag/student.ts:222-249` sanitizes all saved student state and `:606-620` registers the actions. A story can gate on the existing status/term/records and route the player to Senate, workplace, hostel, or Student Union with current UI blockers.
3. **Social memory/follow-up.** `src/game/systems/social.ts:210-250` and `:253-272` already remember deeds and schedule delayed consequences. A named campus NPC can reuse `Relationship.m`, `followUps`, `friend.made`, and NPC notices instead of adding another conversation database.
4. **Tables and campus shared leaderboard.** `src/campus/unilag/games.ts:50-70`, `:238-255`, and `server/routes/campus.ts:28-77` provide Whot/table registry, one-per-day score records, server-owned weekly scans, and a shared goal. Add one configured event/project definition and one idempotent contribution operation.
5. **Wallet/ledger and transactional claims.** `src/game/systems/missions.ts:166-183` is the model for exactly-once rewards; `server/routes/growth.ts:222-229` is the model for server-side durable claims. Story/project rewards should use the same wallet API, ledger reason, and retry key rather than direct balance mutation.

## Proposal boundary

The evidence supports a small first implementation around “Hostel Hustle”: one new branching story slice/content file alongside (rather than replacing) the existing player-authored home-scene system, one recurring campus NPC represented through existing social memory, chapter transitions driven by existing campus/career/table events, and one shared Whot project contribution with a visible campus summary. Keep the existing admissions, semester, hostel, jobs, social relationship, table, wallet, mission, and telemetry owners intact. The source audit does not justify changing economy constants or adding a general content editor before a fresh simulator comparison and focused acceptance evidence.
